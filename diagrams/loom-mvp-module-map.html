Loom MVP 产品模块运作图

核心闭环：Codex 理解语义，diagram.json 保存事实，Workspace 负责人的视觉判断，Renderer 把它变成可见的 2.5D 等轴分析图。

真正的系统中心

  • • 不是 Codex，也不是 iCraft，而是 diagram.json。
  • • Codex 修改“图表达什么”。
  • • Workspace 修改“图怎样被构成和呈现”。
  • • 两边都通过 Diagram Core 安全写入。

语义与视觉分工

  • • Component Template 把语义映射为可调 Scene。
  • • Layout 生成草稿，Human Override 保留人工判断。
  • • Renderer 只负责“怎样画出来”。
  • • 2.5D overlay 保证路线和标注的可读性。

MVP 的停止与通过条件

  • • 先用 Golden Case 验证七种形态能否被辨认。
  • • iCraft 是 Adapter 候选，不是产品单点依赖。
  • • 最终标准不是“成功渲染”，而是作品集可用。
  • • 端到端验收必须从真实 Codex 请求开始。
先把它想成一场舞台排练

Codex 像帮你整理剧本的编剧；diagram.json 是所有人共同遵循的剧本；Component Template 是道具库；Layout 是第一次排走位；Workspace 是导演台；Renderer 是把走位和道具真正摆上舞台的人；PNG 则是最后交给作品集的定妆照。

快速代入案例 · Flovvas Golden Case

“帮我把 Flovvas 从线性对话演化为复利工作空间的过程画成一张 3D 等轴分析图。”

1 · Codex 理解语义

识别 LINE、BRANCH、CARD、FIELD、ARCHIVE、CONTEXT、WORKBENCH，以及它们之间的六次转化。

由 M6 负责。
2 · 创建正式资产

Core 创建节点、关系、阶段区和标注，校验引用后原子保存到 diagram.json。

由 M1 负责。
3 · 选择形态并排草稿

Component 提供七种参数化形态，Layout 生成双 A4、左下到右上的初始构图。

由 M2 + M3 负责。
4 · 人工导演构图

作者在 Workspace 中拖动、旋转、缩放、调整路线和标注；修改写入 Human Override。

由 M5 负责。
5 · Renderer 呈现场景

Reference Renderer 或获准的 iCraft Adapter 生成 3D 节点与可读的 2.5D 路线、标注层。

由 M4 负责。
6 · 导出并验收

导出完整跨页 PNG；重开文件、再次让 Codex 修改，确认人工构图没有被破坏。

由 M7 + M8 负责。

最后得到：一份仍可被 Codex 和 Workspace 继续修改的 diagram.json，以及一张被作者接受进入真实作品集排版的双 A4 等轴分析图 PNG。
